# 🏛️ 01. Архитектура и философия движка уведомлений

## 1. Парадигма Code-as-Configuration и управление триггерами

В платформе **Atena School** действует строгая архитектурная политика в отношении бизнес-логики: **Zero Business Logic in Database Triggers (SQL Triggers)**. Все триггеры уровня SQL (`BEFORE/AFTER INSERT/UPDATE` в PostgreSQL) вынесены в код приложений.

### Почему бизнес-логика вынесена из SQL-триггеров:
1. **Проблема рассинхронизации окружений (Dev vs Prod):**
   * SQL-триггеры, созданные напрямую в базе, легко забыть перенести в миграции, что вызывает скрытый дрифт сред.
2. **Скрытые сайд-эффекты (Hidden Side Effects):**
   * Изменение одной таблицы в SQL не должно неявно порождать каскадные обновления или сетевые HTTP-вызовы в сторонние сервисы (Resend, Telegram).
3. **Изолированное Unit-тестирование:**
   * Логику условий и шаблонизации можно моментально и изолированно протестировать в `vitest` и `jest` на моках.
4. **Типобезопасность (Type-Safety) и версионирование в Git:**
   * Базовые системные правила (`SYSTEM_TRIGGERS`), схемы событий (`SYSTEM_EVENTS_REGISTRY`) и дефолтные пресеты блоков зафиксированы в TypeScript. Опечатки в полях отлавливаются на этапе сборки `pnpm build`.

## 2. Архитектура двух уровней: Core Engine и Backend/Admin

Система уведомлений состоит из двух дополняющих друг друга уровней:

```
┌────────────────────────────────────────────────────────────────────────┐
│                        apps/landing (Чекаут)                           │

│  - Чтение профиля школы и шаблонов через Supabase Client               │
└──────────────────────────────────┬─────────────────────────────────────┘
                                   │
                                   ▼
┌────────────────────────────────────────────────────────────────────────┐
│                    @atena/core (Ядро нотификаций)                      │
│  - Реестр базовых триггеров: SYSTEM_TRIGGERS                           │

│  - Визуальный компилятор: block-compiler.ts (HTML & Telegram)          │
│  - Транспорты: Resend API (Exponential Retry) & Telegram Bot API       │
```

## 3. Бизнес-контекст: Итальянская языковая школа

Движок уведомлений обслуживает специфические юридические и фискальные требования итальянской языковой ассоциации:

### 💶 Правило двух платежей (Two-Payment Rule)
Каждое бронирование разделяется на две финансовые составляющие:
1. `type='registration_fee'` — ежегодный членский взнос ассоциации (**Quota Associativa / Iscrizione = €30.00**).
2. `type='payment'` — оплата самого образовательного курса (**Quota Corso**).

*В уведомлениях и квитанциях эта разбивка всегда отображается явно с расчетом остатка к оплате.*

### 👨‍👩‍👧 Режим "Для ребенка" (`isForChild`)
Если родитель оформляет курс для несовершеннолетнего:
* **Покупатель / Заказчик (`purchaser_*`):** родитель (его email, телефон, Codice Fiscale).
* **Студент (`student_*`):** ребенок (имя, дата и место рождения, персональный Codice Fiscale).
* **Членская карта и взнос €30:** оформляются на **студента** (ребенка), а финансовый чек направляется родителю.

### 💼 Фискальные реквизиты (Fattura Elettronica)
Для корпоративных клиентов и резидентов Италии письма и алерты содержат поля **Codice SDI** (система обмена данными налоговой) и адрес **PEC** (сертифицированная почта).

## 4. White-Label и динамический брендинг

Система спроектирована как полноценный **White-Label движок**:
* Все реквизиты школы (название, юридический адрес, телефон, email секретариата, IBAN для банковских переводов, логотипы, соцсети) подтягиваются динамически через сервис `getSchoolProfile(supabase)`.
* Доменные URL (`site_url`, `app_url`, `admin_url`) и секреты провайдеров (`RESEND_API_KEY`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`) загружаются из таблицы `app_settings` и `integration_secrets` с безопасным фоллбэком на переменные окружения `process.env`.
* Это позволяет разворачивать платформу для разных школ или филиалов без изменения исходного кода движка.
