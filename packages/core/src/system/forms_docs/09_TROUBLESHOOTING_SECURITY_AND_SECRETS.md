# 🛡️ 09. Безопасность, RLS-политики и Устранение неполадок

Спецификация политик безопасности Row Level Security (RLS), защиты системных данных и диагностики неполадок модуля форм.

---

## 🔒 1. Политики безопасности Row Level Security (RLS)

Таблица `public.form_templates` защищена на уровне ядра PostgreSQL:

1. **Публичный доступ на чтение (Public Read):**
   ```sql
   CREATE POLICY "Public can view active form templates"
     ON public.form_templates
     FOR SELECT
     USING (is_active = true);
   ```
   * Анонимные клиенты и лендинг могут читать **только активные** шаблоны форм. Черновики и отключенные формы недоступны для публичного API.

2. **Административный доступ (Admin Access):**
   ```sql
   CREATE POLICY "Authenticated users have full access to form templates"
     ON public.form_templates
     FOR ALL
     USING (auth.role() = 'authenticated' OR auth.role() = 'service_role');
   ```
   * Создание, редактирование и удаление форм строго ограничено авторизованными пользователями с ролью `admin` или бэкенд-сервисом (`service_role`).

---

## 🛡️ 2. Защита целостности данных

1. **Невозможность удаления дефолтного шаблона:**
   - Попытка вызвать `DELETE /api/admin/forms/:id` для формы с `is_default = true` блокируется на уровне `FormsService` с возвратом ошибки `400 Bad Request`.
2. **Защита Core полей от удаления:**
   - Базовые фискальные поля покупателя (Имя, Фамилия, Email, Телефон, Codice Fiscale) не входят в список редактируемых кастомных полей и защищены на уровне архитектуры.
3. **Безопасность SQL Injection:**
   - Все запросы выполняются через Supabase PostgREST клиент и параметризованные запросы с автоматическим экранированием JSONB-ключей.

## 🩺 3. Диагностика и устранение неполадок (Troubleshooting)

### Проблема 1: На лендинге отображаются не те кастомные поля
* **Причина:** Курс привязан к категории, для которой создан отдельный шаблон, переопределяющий дефолтный.
* **Решение:** Проверьте вкладку «Targeting» в визуальном конструкторе формы и убедитесь, что `category_slug` или `course_id` настроены корректно.

### Проблема 2: Поле было заполнено в старой заявке, но удалено из формы
* **Поведение:** Вся история сохранена в `bookings.custom_fields` в PostgreSQL. Удаление поля из шаблона не стирает ранее собранные данные из базы.

### Проблема 3: Переменная `{{custom.my_field}}` в письме пустая
* **Причина:** Опечатка в ключе поля (key) или клиент не заполнил необязательное поле при оформлении.
* **Решение:** Проверьте системный ключ в конструкторе форм и убедитесь, что в шаблоне используется точный ключ `{{my_field}}` или `{{custom.my_field}}`.
