# Atena School — Бизнес-флоу и Логика

> Этот документ описывает **бизнес-цели** и **логику работы** каждого флоу.
> Читай прежде чем менять что-либо связанное с бронированием, оплатами, расписанием или ЛК.

---

## 🎯 Главная бизнес-цель платформы

Школа хочет **убрать бумажную рутину**. Каждая запись на курс должна автоматически:
1. Сохранить данные клиента (студент + покупатель)
2. Проверить взнос €30 и не взять его дважды
3. Создать расписание уроков
4. Появиться в отчётности (платежи, журнал)
5. Дать клиенту доступ к своему расписанию в ЛК

---

## 👥 Три точки входа — три разные роли

```
Клиент сам                   Клиент в школе              Клиент в ЛК
(apps/landing)               (apps/admin)                (apps/app)
       │                            │                          │
       ▼                            ▼                          ▼
Выбирает курс сам         Секретарь помогает         Видит своё расписание
Платит картой или         записаться и принять       Следит за уроками
бронирует без оплаты      оплату наличными/POS       Планирует гибкие уроки
```

Все три пути ведут в одну БД. Результат одинаковый — запись в `bookings` + уроки в `lessons`.

## 💶 Годовой взнос €30 — бизнес-смысл

**Почему он существует:**
По итальянскому законодательству школа как ассоциация обязана брать ежегодный членский взнос.
€30 = одноразово в год, независимо от количества курсов.

**Что это значит для системы:**
- При первой покупке в учебном году → взнос €30 добавляется автоматически
- При второй покупке в том же году → взнос = €0, система это проверяет сама
- Проверка идёт по CF (Codice Fiscale) ИЛИ email ИЛИ телефон — любого из трёх достаточно

**Для ребёнка:**
- Взнос платится за ребёнка, а не за родителя
- Проверяется CF ребёнка (не родителя)
- Если ребёнок уже записан → его CF найдётся → взнос = €0

**В БД:**
- Взнос записывается в `annual_memberships` с полями `tax_code`, `email`, `phone`, `student_id`
- Это позволяет найти запись любым из трёх идентификаторов при следующей покупке

## 📋 Флоу 1: Клиент записывается сам на лендинге

**Бизнес-цель:** Минимум действий секретаря. Клиент всё делает сам.

```
Клиент выбирает курс
       │
       ▼
Вводит данные (своё CF или CF ребёнка)
       │
       ▼
Система проверяет взнос (GET /check-fee-status)
  → Если нет → добавляет €30 к сумме
  → Если есть → сумма только за курс
       │
       ▼
Выбирает оплату:
  A) Всё картой (Stripe) → оплата сейчас → booking.status = 'completed'
  B) Курс картой, взнос в школе → Stripe только за курс, взнос pending
  C) Забронировать без оплаты → booking.status = 'reserved', платит при визите
       │
       ▼
Система создаёт:
  bookings (запись заказа)
  students (профиль студента)
  annual_memberships (если взнос > 0)
  payments (запись платежа)
  lessons (расписание уроков на весь месяц)
       │
       ▼
Клиент получает письмо → заходит в ЛК → видит расписание
```

**Важно:** Лендинг — эталонная реализация. Логика в `apps/landing/` не меняется.
Любой новый флоу бронирования должен **копировать** эту последовательность, не изобретать свою.

## 🏢 Флоу 2: Запись через рецепцию (Reception Wizard)

**Бизнес-цель:** Секретарь принимает клиента лично — быстро вносит данные, принимает оплату.

**Почему это отдельный флоу:**
- Клиент может не иметь email / не хотеть регистрироваться
- Оплата наличными или через POS (не Stripe)
- Секретарь может записать ребёнка которого нет в системе
- Данные могут быть неполными (нет CF — только имя и телефон)

**Шаги:**

### Шаг 1: Клиент (кто платит и кто учится)
Секретарь вводит email/CF клиента → система автоматически ищет существующего клиента.

**Зачем автопоиск:** Если клиент уже покупал курс → его данные автозаполняются.
Секретарь не вводит одно и то же дважды. Это экономит время и исключает опечатки.

Если запись для ребёнка → отдельные поля: имя ребёнка + его CF.
Взнос проверяется по CF ребёнка (не родителя).

### Шаг 2: Курс и дата
Секретарь выбирает курс → система показывает только допустимые дни в календаре.
Клиент выбирает дату начала → система показывает сколько уроков и когда последний.

**Зачем превью:** Клиент сразу видит "8 lezioni, ultima il 15 settembre" — и соглашается.
Нет сюрпризов после записи.

### Шаг 3: Оплата
- Сумма за курс → автозаполняется из прайса
- Взнос → €30 или €0 (уже проверено на шаге 1)
- Метод: Contanti / POS / Bonifico
- Статус: 
  - `reserved` = клиент заплатит потом (бронь зафиксирована, место занято)
  - `completed` = деньги уже получены

**Важно про `reserved`:**
Это не значит что бронь ненастоящая. Место в группе занято.
Секретарь потом в модуле `/pagamenti` меняет статус платежа на `succeeded` когда деньги придут.
При этом `bookings.amount_paid` и `payment_status` обновляются автоматически.

### После submit:
Система записывает всё (bookings, students, annual_memberships, payments×2, lessons).
Клиент получает место в расписании.
Если клиент потом создаст аккаунт в ЛК с тем же email → его бронь автоматически прилинкуется к аккаунту.

## 📱 Флоу 3: Клиент заходит в Личный Кабинет

**Бизнес-цель:** Клиент сам видит своё расписание. Меньше звонков в школу.

```
Клиент входит в ЛК (Supabase Auth)
       │
       ▼
Система ищет брони по email (purchaser_email OR student_email)
  → Прилинковывает user_id к найденным бронированиям
  → Прилинковывает user_id к платежам
  → Прилинковывает user_id к студенту
       │
       ▼
Для каждой брони показывает:
  - Название курса, учитель
  - Расписание (читает из таблицы lessons — реальные даты)
  - Статус оплаты (paid / reserved / pending)
```

**Типы курсов — разное отображение:**

| Тип | Что видит клиент |
|---|---|
| Групповой фиксированный | Полный список дат "Lunedì 4 ago 18:00" и т.д. |
| Пакет уроков | Счётчик "3 / 10 lezioni" + кнопка запланировать следующий |
| C1/C2 Advanced | "In coordinamento con il docente" — расписание согласуется |
| EIPASS | "30 ore totali" — объём, а не конкретные даты |

## 💰 Флоу оплат — как работает кассовая книга

**Бизнес-цель:** Школе нужно видеть все деньги которые должны прийти и которые уже пришли.
Отдельно — за курсы, отдельно — за взносы. Для отчётности.

### Структура записей для одной брони:

```
booking #abc123
├── payments[0]: type='payment', amount=109.80, status='pending', notes='Corso: Movers'
└── payments[1]: type='registration_fee', amount=30.00, status='pending', notes='Quota d'iscrizione A.A. 2026/2027'
```

**Почему две записи, а не одна:**
- В модуле `/pagamenti` видно за что конкретно пришли деньги
- Можно посчитать суммарные взносы за год отдельно от выручки за курсы
- Можно обновить статус взноса и статус курса независимо

### Когда клиент платит наличными (статус меняется):
Секретарь в `/pagamenti` → находит нужную запись → меняет `status: pending → succeeded`.
Система автоматически: пересчитывает `bookings.amount_paid` и ставит `bookings.payment_status = 'completed'`.

### Онлайн оплата (Stripe):
`provider = 'stripe'`, `provider_transaction_id = 'pi_xxx'` → кликабельная ссылка на транзакцию.
Stripe Webhook → автоматически создаёт/обновляет записи в `payments`.

## 🗓️ Флоу расписания и уроков

**Бизнес-цель:** Секретарь не вводит каждый урок вручную. Расписание генерируется автоматически.

### Как генерируются уроки:
При создании брони → `calculateLessonDates(startDate, startTime, category, scheduleDays, duration)`.
Функция смотрит на месяц вперёд и создаёт уроки только в разрешённые дни курса.

**Пример:** Курс Movers, Пн+Ср, начало 10 августа →
```
Пн 10 авг 16:15 — 17:30
Ср 12 авг 16:15 — 17:30
Пн 17 авг 16:15 — 17:30
... (итого 16 уроков за месяц)
```

### Почему важно читать из `lessons`, а не пересчитывать:
Если секретарь перенёс урок (болезнь, праздник) → изменения в таблице `lessons`.
Клиент в ЛК должен видеть актуальные даты, а не первоначальный расчёт.
Поэтому `portal.service` читает из `lessons` как из источника правды.

## ⚡ Ключевые бизнес-правила (must know перед кодингом)

1. **Взнос — ровно один раз в год.** CF (Codice Fiscale) — **основной** идентификатор, проверяется первым и отдельно. Email и телефон — дополнительные, проверяются только если CF не введён или не дал результат. **Никогда не подставлять CF родителя вместо CF ребёнка.**
2. **`reserved` ≠ фейковая бронь.** Место занято. Только деньги ещё не получены.
3. **Уроки генерирует `calculateLessonDates()`.** Никакой другой логики — везде одна функция.
4. **Два платежа на бронь** — курс и взнос раздельно. Не сливать в один.
5. **Когда payment.status = 'succeeded'** → booking обновляется автоматически. Руками не трогать.
6. **ЛК находит брони по email.** Не нужен user_id для поиска — user_id прилинкуется потом автоматически.
7. **isForChild = true** → взнос проверяется **исключительно по реквизитам ребёнка (студента)** (`studentTaxCode` / `studentEmail`). Пока реквизиты ребёнка не введены — проверять почту/CF родителя запрещено, взнос равен **€0.00**. Проверка запускается только после ввода данных ребёнка.
8. **EIPASS** → уроки не генерируются (null), только часы. Отдельное отображение в ЛК.
