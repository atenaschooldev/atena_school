# Инструкция для ИИ-агентов по разработке проекта (AI Guidelines & Manifesto)

Этот документ предназначен для ИИ-ассистентов и разработчиков, работающих над проектом **Atena School CRM**. Он описывает технологический стек, архитектурную философию, правила написания кода и идеологию проекта. Любые изменения в проекте должны строго следовать этим правилам.

---

## 🛠 Технологический Стек

* **Backend Framework**: NestJS (последней стабильной версии, v10+) с адаптером `@nestjs/platform-fastify` для высокой производительности.
* **Database Layer**: PostgreSQL (хостинг на Supabase) + Prisma ORM (последней стабильной версии, v5+).
* **Frontend**: Dart & Flutter.
* **API Spec**: OpenAPI / Swagger (автогенерация из кода NestJS).
* **Типы и Клиент**: `swagger_parser` + `retrofit` + `json_serializable` во Flutter-проекте.

## 💻 Локальное развертывание (Local Development Setup)

Для быстрого развертывания проекта в локальном окружении выполните следующие шаги:

1. **Установка зависимостей**:
   ```bash
   npm install
   ```
2. **Настройка переменных окружения**:
   * Скопируйте файл с примером окружения:
     ```bash
     cp env.example .env
     ```
   * Откройте созданный файл `.env` и заполните обязательные переменные (параметры БД, JWT-ключи Supabase). Это необходимо для успешного прохождения встроенной Fail-Fast проверки при старте бэкенда.
3. **Запуск локальной базы данных**:
   * Для локальной разработки используется локальный инстанс Supabase CLI. Запустите его командой:
     ```bash
     supabase start
     ```
     *(Это поднимет локальные Docker-контейнеры PostgreSQL, Auth, Storage и др. Убедитесь, что Docker Desktop запущен).*
3. **Генерация Prisma Client**:
   ```bash
   npx prisma generate
   ```
4. **Применение локальных миграций**:
   ```bash
   npx prisma migrate dev
   ```
5. **Генерация спецификации Swagger**:
   ```bash
   npm run generate:spec
   ```
6. **Запуск сервера в режиме разработки**:
   ```bash
   npm run start:dev
   ```

## 🏛 Архитектурная Философия и Идеология

Мы следуем принципам **Чистой Архитектуры (Clean Architecture)** с элементами **Feature-First (вертикальные слайсы)**. 

### 1. Абсолютная модульность и слабая связанность (Loose Coupling)
* Любые доработки или исправления внутри одной фичи не должны ломать или затрагивать логику других фич. Модули взаимодействуют друг с другом исключительно через публичные интерфейсы/сервисы.
* Модули изолированы друг от друга: любой из них можно отключить, удалить или полностью перепроектировать без нарушения работы остальной системы.

### 2. Независимость от вендоров, библиотек и сторонних пакетов
* **Базы данных и ORM**: Полное разделение интерфейсов и реализаций (`Repository Pattern`). При необходимости заменить Prisma на TypeORM / сырые SQL-запросы или перенести данные с PostgreSQL на другую СУБД, изменения вносятся исключительно в файлы директории `impl/` соответствующей фичи. Сервисы и контроллеры не меняются.
* **Внешние пакеты и библиотеки**: Любые сторонние инструменты (генераторы PDF, почтовые клиенты, интеграция с календарями, дисками и платежными шлюзами) подключаются только через абстрактные интерфейсы (например, в `src/shared/abstractions/`). Замена вендора (например, переход с WeasyPrint на Puppeteer или с одного API на другое) должна решаться заменой одной строки регистрации класса в DI-контейнере.
* **Динамическое переключение**: Внедрение внешних интеграций должно проектироваться так, чтобы при необходимости можно было переключать провайдеров «на лету» (например, через переменные в `.env` или настройки в панели администратора), без переписывания логики приложения.

### 3. Главное правило: Независимость от вендора данных
Бизнес-логика (сервисы) и транспортный уровень (контроллеры) не должны ничего знать о конкретной СУБД или ORM. Вся работа с базой данных осуществляется исключительно через **интерфейсы репозиториев (Repository Pattern)**.

### Глобальная структура проекта (Global Directory Structure)
Все исходные файлы проекта располагаются в директории `src/` по следующей канонической структуре:
```
src/
├── core/               # Глобальные сквозные компоненты (фильтры ошибок, интерцепторы, гварды, глобальный Prisma-модуль)
├── shared/             # Общие вспомогательные и переиспользуемые ресурсы
│   ├── abstractions/   # Абстрактные интерфейсы внешних сервисов (почта, Google Drive и др.)
│   ├── dtos/           # Общие классы DTO (PaginationQueryDto, PaginatedResponseDto и др.)
│   ├── prisma/         # Глобальные расширения Prisma Client (soft-delete extension и др.)
│   └── temp/           # Временные файлы (загрузка/выгрузка медиа, гарантированно очищаемые автоматически)
└── features/           # Изолированные бизнес-фичи (вертикальные слайсы приложения)
```

### Архитектурные требования к фичам:
Каждая бизнес-фича должна быть изолирована в своей директории в `src/features/` и иметь следующую внутреннюю структуру:
1. **Доменные модели (Domain Entities)**: Описываются в `domain/<feature>.entity.ts`. Это чистые классы TypeScript, описывающие бизнес-сущность. В них **запрещено** импортировать типы из `@prisma/client` или использовать декораторы баз данных.
2. **Интерфейс репозитория**: Описывается в `domain/<feature>s.repository.interface.ts` как абстрактный класс. Задает методы работы с хранилищем.
3. **Реализация репозитория**: Находится в `impl/prisma-<feature>s.repository.ts`. Это единственный файл в фиче, который имеет право импортировать `PrismaService` и работать с методами `@prisma/client`. Он отвечает за маппинг данных из формата БД в доменную сущность.
4. **Бизнес-сервис**: Зависит только от абстрактного класса репозитория. Внедрение осуществляется через DI-контейнер NestJS:
   ```typescript
   constructor(private readonly repository: UsersRepository) {} // Внедрение абстракции
   ```
5. **Модуль**: Связывает интерфейс репозитория с его конкретной реализацией (например, Prisma) и регистрирует контроллеры и сервисы:
   ```typescript
   providers: [
     FeatureService,
     {
       provide: FeaturesRepository,
       useClass: PrismaFeaturesRepository,
     },
   ]
   ```

## 🚫 Строгие правила для ИИ-агентов (Do's and Don'ts)

* ❌ **НИКОГДА** не внедряйте `PrismaService` напрямую в бизнес-сервисы (`*.service.ts`) или контроллеры. Все операции с БД должны идти через абстрактный репозиторий.
* ❌ **НИКОГДА** не используйте тип `any` в TypeScript-коде. При необходимости используйте `unknown` с явным сужением типа (type narrowing) или `Record<string, unknown>`. В `tsconfig.json` принудительно включены `"strict": true` и `"noImplicitAny": true`.
* ❌ **НИКОГДА** не пишите хардкод-заглушки (mock данные) при создании или изменении фич, если для них уже спроектирована и валидирована схема базы данных.
* ❌ **НИКОГДА** не удаляйте и не форматируйте чужой/соседний код, не относящийся к вашей текущей задаче (принцип минимального хирургического вмешательства).
* ❌ **НИКОГДА** не игнорируйте автогенерацию типов. После изменения любого контроллера или DTO на бэкенде, обязательно запустите генерацию схемы:
  ```bash
  # В бэкенде:
  npm run generate:spec
  # Во фронтенде:
  dart run swagger_parser && dart run build_runner build --delete-conflicting-outputs
  ```
* 🟢 **ВСЕГДА** проверяйте сборку проекта с помощью `npm run build` перед коммитом изменений. Любые ошибки типов TypeScript должны быть устранены.
* 🟢 **ВСЕГДА** объявляйте внедряемые зависимости в конструкторах сервисов, репозиториев и контроллеров с модификаторами `private readonly` (например, `constructor(private readonly service: StudentsService) {}`) для гарантии иммутабельности зависимостей.
* 🟢 **ВСЕГДА** пишите понятные названия файлов для документации (избегайте дублирования `README.md` в подпапках, используйте понятные `CORE.md`, `SHARED.md`, `AUTH.md` и т.д.).
* 🟢 **ВСЕГДА** используйте транзакции (`this.prisma.$transaction`) при групповых изменениях или связанных операциях записи/удаления в репозиториях для обеспечения консистентности данных.

## 🏷 Соглашения по именованию и кодированию (Naming & Coding Conventions)

Для предотвращения рассинхронизации кодовых баз бэкенда и фронтенда, все разработчики и ИИ-агенты должны строго следовать этим стандартам:

### 1. Правила именования файлов и классов
* **Директории фич, Сервисы, Контроллеры, Модули и Репозитории** именуются во **множественном числе** (например, `students.controller.ts`, `StudentsService`, `StudentsRepository`, `students.module.ts`, `PrismaStudentsRepository`).
* **Доменные сущности и DTO** именуются в **единственном числе** (например, `student.entity.ts`, `StudentEntity`, `create-user.dto.ts`, `CreateUserDto`).
* **Суффиксы классов и названия файлов**:
  * **Сервисы**: Классы должны иметь суффикс `Service` в CamelCase и множественное число (например, `StudentsService`). Имя файла в kebab-case: `students.service.ts`.
  * **Репозитории (Интерфейсы)**: Классы должны иметь суффикс `Repository` в CamelCase и множественное число (например, `StudentsRepository`). Имя файла: `students.repository.interface.ts`.
  * **Репозитории (Реализация Prisma)**: Классы должны иметь префикс `Prisma` и суффикс `Repository` в CamelCase (например, `PrismaStudentsRepository`). Имя файла: `prisma-students.repository.ts`.
  * **Контроллеры**: Классы должны иметь суффикс `Controller` в CamelCase и множественное число (например, `StudentsController`). Имя файла в kebab-case: `students.controller.ts`.
  * **Модули**: Классы должны иметь суффикс `Module` в CamelCase и множественное число (например, `StudentsModule`). Имя файла в kebab-case: `students.module.ts`.
  * **Гварды (Guards)**: Классы должны иметь суффикс `Guard` в CamelCase (например, `RolesGuard`, `AuthGuard`). Имя файла: `roles.guard.ts`.
  * **Интерцепторы (Interceptors)**: Классы должны иметь суффикс `Interceptor` в CamelCase (например, `AuditInterceptor`). Имя файла: `audit.interceptor.ts`.
  * **Фильтры ошибок (Exception Filters)**: Классы должны иметь суффикс `Filter` в CamelCase (например, `AllExceptionsFilter`). Имя файла: `all-exceptions.filter.ts`.
  * **Пайпы (Pipes)**: Классы должны иметь суффикс `Pipe` в CamelCase (например, `ValidationPipe`). Имя файла: `validation.pipe.ts`.
* **DTO именование**: Классы DTO должны оканчиваться на `Dto` и использовать префикс-действие в CamelCase (например, `CreateUserDto`, `UpdateUserDto`), а не суффикс-действие (запрещено: `UserCreateDto`, `UserUpdateDto`). Имя файла пишется в kebab-case (например, `create-user.dto.ts`).
* **События/хуки**: При использовании шины событий (EventEmitter) или очередей события должны именоваться в стиле `kebab-case` с разделением точками в формате `сущность.действие` (например, `user.created`, `lesson.completed`, `payment.received`).

### 2. Единая стратегия обработки ошибок (Error Handling Strategy)
* **Использование исключений**: Используйте встроенные исключения NestJS (`NotFoundException`, `ForbiddenException`, `BadRequestException`, `ConflictException`) вместо выбрасывания стандартных `throw new Error()`.
* **Пользовательские исключения**: Если требуется специфический доменный контекст, создавайте кастомные классы ошибок, расширяющие стандартные HTTP-исключения NestJS (например, `class StudentNotFoundException extends NotFoundException {}`), и выбрасывайте их в бизнес-сервисах.
* **Глобальный фильтр**: Все ошибки перехватываются и форматируются через [AllExceptionsFilter](file:///Users/krimson/PROJECTS/nest_backend/src/core/filters/all-exceptions.filter.ts). Это гарантирует, что клиент всегда получает единообразный JSON-ответ следующего формата:
  ```json
  {
    "detail": "Сообщение об ошибке",
    "code": "ERROR_CODE",
    "type": "ErrorType"
  }
  ```
  *(Для ошибок валидации `class-validator` массив сообщений склеивается глобальным фильтром в одну строку `detail`).*
* **Логирование**: Ошибки записываются через стандартный `Logger` NestJS из пакета `@nestjs/common`. В production-окружении настраивается интеграция с внешней системой мониторинга (например, Sentry) на уровне глобального фильтра.

### 3. Формат ответов API (Response Shape) и Пагинация (Pagination)
* **Одиночные объекты**: Эндпоинты возвращают объект напрямую (`{ "id": "...", "name": "..." }`).
* **Непагинированные списки**: Возвращаются в виде сырого массива объектов (`[...]`).
* **Пагинированные списки**: Вся пагинация в проекте является **Offset-based** (страничной) и должна строго реализовываться с использованием единых DTO классов из [pagination.dto.ts](file:///Users/krimson/PROJECTS/nest_backend/src/shared/dtos/pagination.dto.ts):
  * Для входящих query-параметров запроса используется класс `PaginationQueryDto` (содержит валидируемые и типизированные свойства `page` и `limit`, а также удобный геттер `offset`).
  * Для исходящих ответов используется обертка `PaginatedResponseDto<T>`, содержащая:
    * `data`: Массив элементов `T[]`.
    * `meta`: Объект `PaginationMetaDto` (содержит `page`, `limit`, `total`, `pages`). Для создания метаданных используйте статический метод `PaginationMetaDto.create(page, limit, total)`.
  * **Лимиты пагинации**: Дефолтное значение `limit` составляет **20** элементов, максимально допустимое значение — **100** элементов. Входящие DTO обязаны использовать валидатор `@Max(100)` для предотвращения перегрузки бэкенда огромными выборками.
  * Формат ответа:
    ```json
    {
      "data": [...],
      "meta": {
        "page": 1,
        "limit": 20,
        "total": 100,
        "pages": 5
      }
    }
    ```
    Это необходимо, чтобы Flutter-клиент мог автоматически десериализовать любой списочный запрос без сбоев.

### 4. Версионирование API (API Versioning)
* **Префикс и версии роутов**: Все эндпоинты бэкенда должны использовать глобальный префикс `/api` и версионирование через URL (например, `/api/v1/students`). Версионирование настраивается глобально в `main.ts` с помощью `app.enableVersioning({ type: VersioningType.URI, defaultVersion: '1' })`.
* **Введение Breaking Changes (ломающих изменений)**:
  * При изменении контракта API (удаление полей, изменение типов данных или структуры ответов), которые ломают обратную совместимость с Flutter-клиентом, создается новый контроллер или роут с новой версией (например, `@Version('2')` или `/api/v2/...`).
  * Для плавного перехода старый контракт помечается как устаревший с помощью декоратора Swagger `@ApiOperation({ deprecated: true })` (для роутов) или `@ApiProperty({ deprecated: true })` (для отдельных полей в DTO) и сохраняет работоспособность на установленный deprecation-период (минимум 1 месяц или до следующего мажорного релиза клиента).

### 5. Работа с файлами и медиа (File & Media Handling)
* **Временное хранение**: При загрузке файлов (договоры, аватары, домашние задания) они обрабатываются в оперативной памяти бэкенда (`multer` с `memoryStorage()`) без сохранения на локальный диск, если их размер не превышает **5 МБ**. Для более крупных файлов (> 5 МБ) используется временная папка `src/shared/temp/`, файлы из которой должны гарантированно удаляться сразу после успешной обработки или загрузки в облако (в блоках `try-finally`).
* **Ограничения и валидация**:
  * Лимиты по размеру: максимум **10 МБ** для общих документов (PDF, DOCX) и максимум **2 МБ** для изображений профилей/аватаров.
  * Разрешенные форматы (Mime Types): Изображения (`image/jpeg`, `image/png`, `image/webp`), Документы (`application/pdf`, `application/vnd.openxmlformats-officedocument.wordprocessingml.document` (docx), `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet` (xlsx)).
  * Валидация выполняется на уровне контроллера с помощью стандартного NestJS `ParseFilePipe` с валидаторами `MaxFileSizeValidator` и `FileTypeValidator`.
  * **Защита от подмены расширения (Magic Bytes Check)**: Для предотвращения загрузки вредоносного кода под видом документов, перед обработкой файла бэкенд должен дополнительно проверять его первые байты (сигнатуру/magic bytes) для подтверждения реального типа контента, отсекая любые несоответствия.
* **Генерация публичных ссылок**:
  * Клиентское приложение никогда не общается напрямую с API Google Drive под сервисным аккаунтом. Бэкенд отвечает за авторизацию, загрузку файлов, а также за генерацию временных публичных ссылок на скачивание (Signed URLs / Shareable links) и передачу их клиенту в JSON-ответах.

## 🛡 Принятые решения по архитектуре и безопасности

* **Управление пользователями и сессиями**: Авторизация всегда выполняется через **Supabase Auth**. Панель администратора на клиенте должна позволять создавать/редактировать пользователей с назначением соответствующих ролей и уровней доступа, которые синхронизируются в локальную таблицу `users`.
* **Эшелонированная защита (Defense-in-Depth)**:
  * На уровне бэкенда NestJS: Контроль бизнес-логики и прав выполнения операций с помощью Guards и Roles.
  * На уровне базы данных Supabase (PostgreSQL): Обязательное включение **RLS (Row Level Security)** для всех таблиц, к которым может быть прямой доступ со стороны клиентов, для изоляции данных на уровне БД.
* **Автоматические миграции**: Разрешено автоматическое создание и выполнение миграций (`npx prisma migrate dev`) **только в dev-окружении**. В production-среде автоматическое применение миграций агентом запрещено — они должны применяться разработчиком вручную.

* **Интеграция внешних API (Big Tech Production Best Practices)**:
  Для работы с внешними провайдерами услуг (календари Google/Outlook, файловые хранилища Google Drive / AWS S3) должен использоваться паттерн **Стратегия (Strategy/Provider Pattern)**:
  1. Объявляется единый абстрактный интерфейс (например, `CalendarService` с методом `createMeeting`).
  2. Создаются обособленные сервисы-реализации для каждого провайдера (`GoogleCalendarService`, `OutlookCalendarService`).
  3. Выбор активного провайдера разрешается через фабрику (`Provider Factory` / NestJS custom provider) на этапе старта приложения (если конфигурация глобальная через `.env`) либо динамически во время выполнения запроса на основе настроек конкретного пользователя/клиента (получение токена доступа конкретного пользователя). Это гарантирует, что бизнес-логика полностью развязана от конкретного SDK интеграции.

## 🔒 Стандарты информационной безопасности (Security Standards)

Все разработчики и ИИ-агенты должны строго следовать стандартам безопасности при написании кода для проекта:

### 1. Защита на уровне БД: Row Level Security (RLS)
* В базе данных Supabase (PostgreSQL) для всех пользовательских таблиц (особенно `students`, `teachers`, `payments`, `grades`, `documents`) должен быть включен RLS.
* Правила RLS должны ограничивать доступ на чтение/запись на основе метаданных авторизованного пользователя (например, `auth.uid() = student_id`).

### 2. Предотвращение DDoS и спама (Rate Limiting)
* Для критичных к спаму эндпоинтов (авторизация, отправка писем, генерация PDF-документов) должен быть настроен лимит запросов (Rate Limiting) через плагин `@fastify/rate-limit`.

### 3. Защита от SQL-инъекций
* Все запросы к БД должны проходить через методы Prisma ORM (которые параметризованы по умолчанию).
* Использование сырых запросов (`$queryRaw`) допускается только в крайних случаях и только через безопасные шаблонные строки Prisma (Prisma.sql) либо с явной параметризацией. Склеивание строк для сборки SQL-запросов **категорически запрещено**.

### 4. Строгая валидация JWT
* Авторизация входящих запросов выполняется через `passport-jwt` на бэкенде.
* Токен должен парситься строго из заголовка `Authorization: Bearer <token>`.
* Подпись токена должна проверяться с использованием `SUPABASE_JWT_SECRET`. Должно контролироваться время жизни токена (`exp`).

### 5. Контроль доступа: RBAC и ABAC
* **RBAC (Role-Based Access Control)**: Ограничение доступа к роутам контроллера выполняется через декоратор `@Roles()` и гвард `RolesGuard`.
* **ABAC (Attribute-Based Access Control)**: Для данных, принадлежащих конкретному пользователю (например, просмотр своих оценок студентом), сервис обязан проверять владение ресурсом:
  ```typescript
  if (user.role === 'student' && user.id !== targetStudentId) {
    throw new ForbiddenException('Нет прав на просмотр чужих данных');
  }
  ```

### 6. Ротация токенов и отзыв сессий (Refresh Token Rotation & Session Invalidation)
* Управление жизненным циклом сессии и ротация Refresh-токенов делегированы на сторону Supabase Auth. Бэкенд должен проверять валидность токена и поддерживать механизмы отзыва сессий при интеграции соответствующих вебхуков.

### 7. Защита транспортного уровня: CORS и Helmet
* Глобальные политики CORS в `main.ts` должны строго ограничивать разрешенные домены (запрещено использовать `origin: '*'` в production-окружении).
* Для защиты от XSS, Clickjacking и MIME-sniffing должен быть подключен пакет `@fastify/helmet` для установки заголовков безопасности (Content Security Policy, HSTS, X-Content-Type-Options и др.).

### 8. Валидация входных данных и Swagger (class-validator, class-transformer, @ApiProperty)
* **Типизация DTO**: Все входящие тела запросов (payloads) и query-параметры должны быть строго типизированы через классы DTO.
* **class-validator**: DTO должны использовать декораторы `class-validator` для валидации типов, форматов (email, uuid, даты) и ограничений длины. Глобальный `ValidationPipe` должен работать в режиме `whitelist: true` и `forbidNonWhitelisted: true`, чтобы автоматически отсекать любые лишние параметры в запросе.
* **class-transformer**: Числовые и булевы query-параметры (а также параметры, передаваемые в URL) обязаны декорироваться декоратором `@Type(() => Number)` или `@Type(() => Boolean)` из пакета `class-transformer`. Без этого при включенном `ValidationPipe` query-параметры останутся строками, и валидаторы типа `@IsInt()` или `@IsBoolean()` тихо провалят запрос.
* **Документирование Swagger (@ApiProperty)**: Все публичные поля классов DTO (входящие параметры и исходящие ответы эндпоинтов) обязаны иметь декоратор `@ApiProperty()` или `@ApiPropertyOptional()` из `@nestjs/swagger` с обязательным указанием понятного `description` и примера `example`. Это гарантирует генерацию полноценной Swagger-спецификации, без которой Flutter-клиент не сможет сгенерировать типы.

### 9. Предотвращение внедрения команд (Command Injection)
* При взаимодействии с операционной системой (например, вызов `weasyprint` через CLI) категорически запрещено передавать невалидированные пользовательские параметры напрямую в командную строку. Аргументы должны передаваться в виде массива через безопасный метод `spawn` (или `execFile`), а не через склеивание командной строки в `exec`.

### 10. Принцип наименьших привилегий (Principle of Least Privilege)
* Доступы к внешним API (например, сервисные аккаунты Google Cloud) должны иметь минимально необходимый набор OAuth-областей (scopes) (например, доступ только к конкретной папке Google Drive или только на запись в Google Calendar, без доступа к личным данным аккаунта).
* Учетная запись базы данных бэкенда не должна обладать правами суперпользователя (`superuser`) в production-окружении.

### 11. Мягкое удаление (Soft Delete)
* Физическое удаление данных из ключевых таблиц (особенно `users`) запрещено. Используется мягкое удаление через флаг активности `isActive = false` (`is_active` в БД) либо статус архивации (`status = 'archived'`).
* **Глобальный фильтр Prisma**: 
  * Глобальное расширение Prisma Client [soft-delete.extension.ts](file:///Users/krimson/PROJECTS/nest_backend/src/shared/prisma/soft-delete.extension.ts) применяется **исключительно к модели `User`** (автоматически подставляет `{ isActive: true }` в запросы `findMany`, `findFirst`, `findUnique` и `count`).
  * Для всех остальных моделей (`Student`, `Teacher`, `Course`, `Schedule` и др.) признак активности или архивации выражается через текстовое поле `status` (например, `status: 'archived'`, `status: 'cancelled'`). Фильтрация по этим статусам **выполняется вручную в соответствующих репозиториях** в зависимости от требований конкретной бизнес-логики (так как отмененные уроки или архивные курсы могут требоваться в отчетах или истории логов).

### 12. Аудит изменений (Audit Logs)
* Любая мутирующая операция записи/обновления/удаления со стороны администраторов должна логироваться через `AuditInterceptor` для обеспечения прослеживаемости действий.

## 🧪 Стратегия тестирования (Testing Strategy)

Тестирование является обязательной частью разработки для обеспечения стабильности CRM. Мы используем следующие стандарты:

### 1. Юнит-тестирование (Unit Testing)
* **Объект тестирования**: Юнит-тестами покрываются исключительно бизнес-сервисы (`*.service.ts`). Мы проверяем корректность логики без обращения к внешним системам.
* **Изоляция и мокирование**: Репозитории и внешние интеграции должны быть полностью изолированы. Запрещено поднимать реальную БД или вызывать реальные API. Зависимости (репозитории) мокируются с помощью `jest.fn()` или встроенных средств `@nestjs/testing`.
* **Качество типов в тестах**: Категорически запрещено использовать тип `any` в тестах. Все моки и тестовые данные должны быть строго типизированы, чтобы соответствовать интерфейсам репозиториев и сущностям.
* **Покрытие (Coverage)**: Устанавливается минимальный порог покрытия кода тестами для бизнес-сервисов — **80%** (Statements/Functions).

### 2. Интеграционное и сквозное тестирование (E2E Testing)
* **Объект тестирования**: E2E-тесты проверяют корректность сквозных сценариев (например, авторизация, запись студента на курс, оплата) путем отправки HTTP-запросов к приложению.
* **Инструменты (Tools)**: Все E2E-тесты пишутся строго с использованием стандартной библиотеки NestJS `@nestjs/testing` совместно с библиотекой **`supertest`** для выполнения HTTP-запросов. Использование сторонних HTTP-клиентов (например, `axios`, `fetch`) внутри тестов запрещено для сохранения единого стиля тестов.
* **Тестовая база данных**: E2E-тесты выполняются исключительно на **отдельной изолированной тестовой БД** (поднимаемой локально разработчиком/CI через Docker Compose или локальный контейнер Supabase). Тестирование на рабочей (dev/prod) базе данных категорически запрещено.
* **Расположение тестов**:
  * Юнит-тесты (`*.spec.ts`) располагаются **рядом с исходным кодом** тестируемого сервиса (в той же директории фичи).
  * E2E-тесты располагаются в обособленной директории `test/` в корне проекта.

## 🪵 Стратегия логирования (Logging Strategy)

Для обеспечения удобства мониторинга и отладки приложения в dev- и production-средах, все логи должны соответствовать следующим правилам:

### 1. Уровни логирования (LogLevels)
* **В dev-окружении (development)**: Включены уровни `debug`, `log`, `warn` и `error`. Логируется подробная отладочная информация (например, SQL-запросы Prisma, шаги аутентификации).
* **В prod-окружении (production)**: Включены только уровни `log` (для информационных системных сообщений при старте приложения), `warn` и `error`. Логи `debug` отключены для избежания переполнения диска и утечки чувствительных данных.

### 2. Формат логов (Log Format)
* **Dev-окружение**: Стандартный текстовый вывод NestJS с подсветкой синтаксиса и понятными метками времени для удобства локального чтения (Plaintext / Colorized console).
* **Prod-окружение**: Все логи пишутся в виде структурированного **JSON**-формата (одна строка — один JSON-объект). Каждый JSON-объект должен содержать:
  ```json
  {
    "timestamp": "2026-06-15T10:52:00.000Z",
    "level": "error",
    "message": "Сообщение об ошибке",
    "context": "StudentsService",
    "trace": "Stack trace (только для error логов)",
    "metadata": { }
  }
  ```
  Это позволяет системам сбора логов (Grafana Loki, Datadog, ELK) корректно индексировать и парсить логи без регулярных выражений.

### 3. Назначение вывода (Log Transport)
* Все логи должны направляться исключительно в стандартные потоки вывода **stdout** (для `debug`, `log`, `warn`) и **stderr** (для `error`).
* **Категорически запрещено** писать файлы логов на диск контейнера или сервера (это нарушает принципы 12-Factor App и создает риски переполнения диска).
* Передача логов во внешние сервисы мониторинга (Grafana Loki, Datadog, Logflare в Supabase) осуществляется агентом логирования инфраструктуры (например, Promtail, Vector или встроенными средствами AWS/Supabase), считывающим stdout контейнера.

Для поддержания стабильности кодовой базы и минимизации ручного вмешательства разработчика, все ИИ-агенты и разработчики должны следовать строгому регламенту сдачи работы:

### 2. Формат коммитов (Commit Guidelines)
Коммиты должны оформляться строго по стандарту **Conventional Commits**:
* `feat: ...` — новая функциональность (например, `feat: add StudentsRepository interface and implementation`).

* `docs: ...` — обновление документации (`docs: update AI guidelines with versioning rules`).
* `refactor: ...` — переработка кода без изменения логики (`refactor: clean up unused imports in StudentsService`).
* `chore: ...` — вспомогательные изменения (`chore: update dependencies in package.json`).

### 3. Работа с несколькими фичами одновременно (Cross-Feature Changes)
Если задача затрагивает несколько изолированных фич:
* **Инфраструктура и БД**: Сначала описываются и проверяются изменения в общих моделях Prisma (`schema.prisma`) и общих интерфейсах.
* **Изолированное внедрение**: Изменения вносятся в каждую фичу независимо. Не смешивайте код разных модулей в одной куче — пишите точечные, изолированные изменения.
* **Поэтапный коммит/ревью**: Сдавайте работу логическими частями. Изменения должны быть разделены так, чтобы кодовая база оставалась в компилируемом и работоспособном состоянии на каждом этапе интеграции (проверка сборки через `npm run build` обязательна после каждого крупного блока изменений). Circular dependencies (циклические зависимости) между фичами категорически запрещены.


## ⚡ Производительность и оптимизация (Performance & Optimization)

Бэкенд проектируется по принципу **"fast by default"**: каждый эндпоинт должен
быть неблокирующим, минимально нагружать БД и быть готов к горизонтальному
масштабированию.

### 1. Асинхронность и неблокирующий Event Loop

* **ВСЕГДА** используйте `async/await` для любых I/O операций. Синхронные
  блокирующие вызовы (`fs.readFileSync`, синхронные криптографические операции,
  тяжёлые вычисления в цикле) в обработчиках запросов **категорически запрещены**
  — они блокируют Event Loop и деградируют производительность всего сервера.
* CPU-интенсивные операции (обработка изображений, сложные вычисления) должны
  выноситься в отдельный **Worker Thread** или делегироваться внешнему сервису.

### 2. Оптимизация запросов к БД (Prisma Query Optimization)

Главный источник деградации производительности в CRM — неэффективные запросы к БД.

* **Запрет N+1 запросов**: категорически запрещено выполнять запросы к БД внутри
  циклов. Для загрузки связанных сущностей используйте `include` или вложенные
  `select` в Prisma для получения всех данных одним запросом:
```typescript
  // ❌ Запрещено — N+1
  const students = await this.repository.findAll();
  for (const student of students) {
    student.courses = await this.coursesRepository.findByStudentId(student.id);
  }

  // ✅ Правильно — один запрос
  const students = await this.repository.findAllWithCourses(); // include: { courses: true }
```
* **Выборка только нужных полей**: используйте `select` вместо получения полной
  модели, если эндпоинту нужны 2-3 поля из 15. Это снижает нагрузку на сеть и
  память:
```typescript
  // Для списочного эндпоинта не тащим все поля модели
  select: { id: true, fullName: true, email: true }
```
* **Обязательное индексирование**: все поля, по которым выполняется фильтрация
  (`where`), сортировка (`orderBy`) или джойны, **обязаны** быть объявлены как
  индексы в `schema.prisma`:
```prisma
  model Payment {
    id        String   @id
    studentId String
    status    String
    createdAt DateTime

    @@index([studentId])
    @@index([status, createdAt])
  }
```
  Отсутствие индекса на часто используемом поле фильтрации — блокирующая ошибка.

### 3. Тяжёлые операции — только через очереди (BullMQ)

Следующие операции **запрещено** выполнять синхронно в рамках HTTP-запроса, так
как они блокируют ответ клиенту и деградируют пропускную способность сервера:

* Генерация PDF-документов (договоры, отчёты)
* Отправка email / SMS уведомлений
* Экспорт данных (Excel, CSV)
* Загрузка и обработка файлов в Google Drive

**Паттерн**: контроллер принимает запрос → помещает задачу в очередь BullMQ →
немедленно возвращает `202 Accepted` с идентификатором задачи (`jobId`) → клиент
получает результат через последующий запрос статуса или push-уведомление.

### 4. Стратегия кэширования (Caching Strategy)

Клиентское приложение на Flutter использует **Drift (локальная SQLite БД)** как
постоянный локальный кэш на устройстве. Это означает, что бэкенд **не получает
повторных запросов** при навигации между экранами или при отсутствии мутирующих
действий (создание / обновление / удаление).

Инвалидация клиентского кэша происходит **только при мутациях**: Flutter сбрасывает
кэш конкретной сущности и выполняет свежий запрос к API исключительно после
операций записи.

Исходя из этого, серверный кэш (Redis и т.д.) **не требуется** для стандартных
CRUD-операций. Серверное кэширование применяется **только** в следующих случаях:

* **Тяжёлые агрегации и отчёты**: суммы платежей за период, статистика
  посещаемости, сводные дашборды — данные, дорогостоящие для пересчёта в БД.
  Кэшируются на уровне сервиса через `@nestjs/cache-manager` с явным TTL.
* **Глобальные справочники**: настройки школы, списки предметов, тарифные планы —
  данные, одинаковые для всех пользователей и редко меняющиеся. При обновлении
  таких данных кэш инвалидируется явным вызовом `cacheManager.del(key)` в
  соответствующем сервисе.

### 5. Сжатие ответов (Response Compression)

В `main.ts` глобально подключён плагин `@fastify/compress`. Для JSON-ответов с
пагинированными списками это даёт 60–80% экономии трафика, что критично для
Flutter-клиента на мобильных сетях.

### 6. Корректное завершение работы (Graceful Shutdown)

* В `main.ts` включены хуки завершения: `app.enableShutdownHooks()`.
* При получении сигнала `SIGTERM` (например, при деплое или перезапуске контейнера)
  приложение перестаёт принимать новые запросы, дожидается завершения активных
  соединений и корректно закрывает пул соединений с БД. Это предотвращает потерю
  данных и ошибки 502 на стороне клиента во время деплоя.
* Эндпоинт `/api/health` возвращает текущий статус сервиса (доступность БД,
  внешних интеграций) и используется балансировщиком нагрузки для проверки
  готовности инстанса.
