# Документация бизнес-фич (`src/features`)

Бизнес-логика приложения спроектирована по принципу **Feature-First (вертикальные слайсы)**. Каждый модуль автономен и содержит всю необходимую структуру для работы: от роутинга запросов до сохранения данных в СУБД.

## Философия слабой связанности (Loose Coupling) и абстракций

1. **Изоляция изменений**: Модификация или добавление новой логики в одном модуле не должны приводить к поломкам или регрессиям в других модулях. Взаимодействие между модулями происходит только через публичные интерфейсы сервисов.
2. **Независимость от вендоров (Vendor-Independence)**: Все взаимодействия с базой данных (Prisma), внешними API (Google Drive, Google Calendar, платежные шлюзы, почта) скрыты за абстрактными контрактами. Это позволяет переключить базу данных или библиотеку в любой момент времени (и настроить переключатели на уровне админ-панели или `.env`), изменив только одну строку регистрации класса в DI-контейнере NestJS.

## Стандартная структура бизнес-модуля

Каждая фича разделена на слои, что предотвращает утечку деталей базы данных (Prisma) в бизнес-логику:

```
src/features/имя_фичи/
├── domain/                          # Доменный слой (чистый TypeScript)
│   ├── имя_фичи.entity.ts           # Чистый TS-класс сущности
│   └── имя_фичи.repository.interface.ts # Абстрактный контракт репозитория
│
├── impl/                            # Слой инфраструктуры СУБД
│   └── prisma-имя_фичи.repository.ts # Конкретная реализация на Prisma ORM
│
├── имя_фичи.controller.ts           # REST API контроллер (HTTP роутинг)
├── имя_фичи.service.ts              # Бизнес-логика (зависит только от абстрактного репозитория)
└── имя_фичи.module.ts               # NestJS-конфигурация (DI-связывание абстракции и реализации)
```

## Обзор 13 бизнес-модулей

1. **`auth`** — авторизация пользователей на основе JWT-токенов Supabase.
2. **`settings`** — обновление личного профиля пользователя (имени, фамилии).
3. **`students`** — ведение карточек учеников: статус обучения, уровень языка, связь с договором.
4. **`teachers`** — профили учителей: опыт работы, преподаваемый предмет, дата найма.
5. **`courses`** — управление учебными курсами: категория, длительность, цена, преподаватель.
6. **`schedules`** — уроки и расписание (создание одиночных уроков и периодическая генерация).
7. **`attendance`** — учет посещаемости занятий: отметка присутствия, примечания и даты.
8. **`grades`** — журнал оценок (выставление баллов за урок и семестровых оценок по навыкам).
9. **`documents`** — создание и хранение PDF-контрактов через `DocumentRenderer`.
10. **`payments`** — выставление счетов на оплату и печать квитанций.
11. **`mail`** — рассылка уведомлений через SMTP с использованием `nodemailer`.
12. **`activity_logs`** — ведение журнала логов для действий администраторов (аудит-лог).
13. **`home`** — формирование дашборда главной страницы: сводные метрики и лента активности.

## Как добавить новую фичу или обновить существующую

Для добавления новой фичи или расширения существующей (например, добавление полей или новых методов запроса), следуйте пошаговому руководству:

### Шаг 1: Опишите схему БД в Prisma
Добавьте новые таблицы/поля в файл [schema.prisma](file:///Users/krimson/PROJECTS/nest_backend/prisma/schema.prisma) и сгенерируйте клиент:
```bash
npx prisma validate
npx prisma generate
```

### Шаг 2: Дополните Доменную Модель (Domain Entity)
В папке `domain/` обновите TS-класс (например, `CourseEntity`), добавив новые поля. Этот класс не должен иметь декораторов ORM или импортов из `@prisma/client`.

### Шаг 3: Обновите Интерфейс Репозитория
Опишите новые методы в интерфейсе (абстрактном классе) репозитория в папке `domain/`. 
```typescript
export abstract class ProductsRepository {
  abstract findActive(): Promise<ProductEntity[]>;
}
```

### Шаг 4: Реализуйте методы в Prisma-репозитории
В папке `impl/` реализуйте объявленные методы в Prisma-репозитории, используя `PrismaService` и маппинг БД-объектов в доменные сущности.

### Шаг 5: Используйте метод в Сервисе
Внедрите репозиторий через конструктор сервиса (завися от абстрактного класса) и вызовите новый метод:
```typescript
@Injectable()
export class ProductsService {
  constructor(private readonly productsRepository: ProductsRepository) {}

  async listActive() {
    return this.productsRepository.findActive();
  }
}
```

### Шаг 6: Обновите DI-провайдер в Модуле
Убедитесь, что абстракция привязана к реализации:
```typescript
{
  provide: ProductsRepository,
  useClass: PrismaProductsRepository,
}
```

### Шаг 7: Сгенерируйте типы для Flutter
После любого изменения эндпоинтов в контроллерах обязательно обновите спецификацию для Flutter:
```bash
# В папке nest_backend:
npm run generate:spec

# В папке frontend:
dart run swagger_parser && dart run build_runner build -d
```
Клиентские модели и Dio-клиенты во Flutter автоматически пересоберутся под новый контракт API.

## 🏷 Стандарты и Соглашения по разработке фич

Все новые фичи должны строго следовать общим соглашениям по кодированию:
1. **Именование файлов и классов**:
   * Сущности (Entities) и DTO — в **единственном числе** (`StudentEntity`, `CreateUserDto`).
   * Контроллеры, Сервисы, Модули и Репозитории — во **множественном числе** (`StudentsService`, `StudentsRepository`).
   * Файлы именуются в формате kebab-case (например, `create-user.dto.ts`), классы — в PascalCase (`CreateUserDto`).
2. **Обработка ошибок**: Использовать только встроенные исключения NestJS (`NotFoundException` и др.) или их доменные наследники. Исключения преобразуются глобальным фильтром в структуру `{ detail, code, type }` для совместимости со спецификацией Flutter.
3. **Формат ответов**: Одиночные объекты возвращаются в чистом виде (JSON), списки без пагинации — сырым массивом `[...]`, списки с пагинацией — в обертке с ключами `data` и `meta` (содержит page, limit, total, pages).
